# 测试规范与机制说明

项目提供**单元测试**、**集成测试**与**需求测试**。浏览器端到端用例作为需求流程运行，也可以在同一条流程中结合其他手段验证。

## 单元测试 (Unit Testing)

- **定位与目录**: 测试单个独立模块（如单个接口），与目标代码同目录存放（如 `src/interface/demo/base/add/t01.test.ts`）。
- **入口与命令**:
  - 由 `scripts/test/unit/run-test.ts` 驱动。
  - 运行 `npm run test:unit`（支持交互选择、`--all` 全量、`--filter <正则>` 筛选、`--no-coverage` 跳过覆盖率、`--open` 打开报告），默认生成覆盖率与测试报告至 `test-outputs/coverage/index.html`。

## 集成测试 (Integration Testing)

- **定位**: 测试多模块组合运行，可借助接口两用性在不启动服务器的情况下直接调用接口逻辑。
- **目录与编写约定**:
  - 存放在 `test/integration/`（参考 `test/integration/demo.ts`），默认导出无参构造的 `集成测试` 子类。
  - 构造函数仅声明名称与配置，数据准备和断言放在 `运行()` 内；模块导入与实例构造阶段不得启动数据库或任务资源。
- **运行边界**: 通过抛错表达失败，禁止自行调用 `process.exit()`；自建资源在 `finally` 中释放，共享单例随命令结束统一退出。
- **入口与命令**:
  - 由 `scripts/test/integration/run-integration.ts` 驱动。
  - 运行 `npm run test:integration`（支持交互选择、`--all` 全量、指定文件名、`--open` 打开报告），报告输出至 `test-outputs/integration-report/index.html`。

## 需求测试 (Requirement Testing)

- **定位与模型**: 以业务需求和验收点为中心，不限定具体测试手段（命令、HTTP、浏览器、人工检查均可）。核心领域模型（需求、验收点、状态迁移、行为、观察、步骤附件、选择等）详见 `src/model/test-requirement/README.md`。
- **目录与编写约定**:
  - 存放在 `test/requirement/`（参考 `test/requirement/demo.ts`，公共封装放 `test/requirement/helper/`），统一使用 `requirement` 命名，不建立平行测试体系。
  - 默认导出无参构造的 `需求测试` 子类，构造时登记需求、流程及是否使用测试服务。`准备数据(工具)` 只返回业务数据。框架将工具与业务数据一起放入流程上下文。
- **执行边界**:
  - 每次流程尝试都会清空并初始化同一份 Web 测试数据库，再准备业务数据和工具。请先退出测试开发套件，并与使用同一数据库的其他测试串行执行。准备阶段可直接造数据，业务行为须通过 UI、HTTP、命令等真实入口执行。观察可通过数据库查询核对结果。整条流程通过后才记下其证明的验收点。标记为人工验收的流程保留在覆盖模型中，执行时跳过。
  - 需要后端的流程在每次尝试时启动测试服务。`工具.服务地址()` 提供地址。工具按步骤记录收到的标准输出和错误输出，`工具.后端日志.读取()` 可查看当前步骤已收到的日志。
  - `工具.浏览器` 可按名称打开、列出、获得和关闭独立会话。引擎在导航、操作、等待、断言或步骤收尾时按需截图，尝试结束收集最终画面与 Trace。`--demo` 开启可见浏览器、提示和动画，业务步骤和断言与默认的 `--auto` 模式相同。
  - `工具.数据库.查询(SQL, 参数, 报告列)` 使用测试数据库的只读连接。业务值通过参数传入。报告隐藏参数和查询结果值，显式列入 `报告列` 的公开字段可展示，最多预览 20 行。查询返回完整结果供断言使用。
  - 行为和观察仍可手动提交文本和图片。手动附件与工具证据归入同一步骤，取证失败单独记录。
- **入口与命令**:
  - 由 `scripts/test/requirement/run-requirement.ts` 驱动。
  - 运行 `npm run test:requirement`。可交互选择，或指定 `--all`、`--scenario=<流程名>`、`--requirement=<需求名>`、`--list`、`--auto` 或 `--demo`。任务参数 `--prepare-only` 可预览计划。
  - 自动模式在 CI 中每条流程最多尝试三次。报告输出至 `test-outputs/requirement-report/`，可按验收点查覆盖，或打开对应的流程尝试查看步骤、附件、失败信息和浏览器 Trace。

## 交互式测试 MCP

AI 直接写浏览器测试时，一个按钮出现波动，就可能等到超时才发现问题，改完还得从头跑。交互式测试让 AI 留在同一个测试现场，自己决定下一步。比如点了「保存」没反应，可以先看页面、日志或数据库，判断是还在处理、已经保存，还是需要修改代码。前端热更新和后端自动重启让它改完可以接着验证。

MCP 提供与需求测试共用的工具。套件把调用参数、结果和证据路径写入本次的 `operations.json`。AI 可以回看记录、加说明、删掉误点、调整顺序或补上断言，浏览器和数据库仍保留现场。整理后用 `record_export` 把选中的操作和断言生成需求测试代码。再次运行时，断言会检查当次操作的结果，报告会显示预期值和实际值。

需要解释关键操作或断言时，可以通过 `record_note` 写一段决策说明，例如「保存后弹窗已关闭，但这还没确认数据落库，所以再查一次数据库」。导出后，说明会随对应步骤出现在报告里。

在 VS Code 按 `F1`，选择「运行任务」→「启动测试环境开发套件」。在 `.env/.env.test.web` 中设置 `TEST_MCP_ENABLED=true` 后，AI 客户端连接终端打印的 MCP 地址即可。
