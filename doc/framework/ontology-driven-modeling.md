# 本体驱动的充血对象建模指南

## 核心理念：概念、内涵与外延

本项目采用**本体驱动的充血对象建模（Ontology-driven Rich Object Modeling）**风格：先明确问题世界中存在哪些概念、每个概念的内涵与外延，再定义伴随概念的操作与概念间的关系。

> **核心约束**：写成类（`class`），意味着承认它是问题世界中的一个概念；类的实例，是该概念外延中的具体实体。类不是代码收纳盒，也不是为了替代模块或函数而存在。

- **内涵（它为什么是这种事物）**：使事物成为该事物的必要属性、稳定关系和不变量，由类的**私有字段、对象引用和校验约束**表达。建模只表达当前系统关心的本质属性。
- **外延（哪些具体实体属于它）**：所有属于该概念的具体实例（如 `new 学生(...)`）。继承或实现抽象契约表示外延的包含关系（`子类外延 ⊆ 父类外延`）。
- **伴随操作（它能做什么）**：概念成立后伴随其存在的领域行为，由类的**公共方法**表达。内涵与操作共同构成类，使类成为概念的可执行定义。

## 充血模型与职责归属

概念同时拥有自身属性、关系、不变量和操作。如果一个操作需要外部函数读取并操纵对象内部数据才能完成，说明对象边界未被完整封装。

- **行为归入概念**：属于某个概念的领域行为必须进入该类（如用 `班级值.获得学生数量()` 和 `订单值.确认()`，而非外部的 `统计班级学生数量(班级值)` 或 `订单服务.确认订单(订单值)`）。
- **顶层函数的边界**：只有不属于任何领域概念的纯工具计算或技术适配，才保留为顶层函数（如转义 HTML、格式化字节数、计算文件哈希、协议格式无状态转换）。

```ts
// 不推荐：贫血数据 + 外部函数/服务操纵
type 订单 = { 订单项们: 订单项[]; 状态: string }
function 计算订单总额(订单值: 订单): 金额 { ... }
function 确认订单(订单值: 订单): void { ... }

// 推荐：属性、规则与操作内聚在类中
class 订单 {
  public 获得总额(): 金额 { ... }
  public 确认(): void { ... }
  public 取消(原因: string): void { ... }
}
```

## 类（`class`）与类型（`type`）的边界

并不是所有结构都应该建成类；“贫血模型”是指本应拥有业务行为的概念退化成了纯数据结构，而纯数据本身本来就应该使用 `type`。

- **使用 `class` 的场景**：问题世界中的真实概念，伴随自身行为、不变量或生命周期（如 `学生`、`班级`、`订单`、`上传会话`）。即使数据很少，只要维护不可被外部替代的规则（如 `金额` 维护精度、币种一致性与加减规则），也应建为类。
- **使用 `type` 的场景**：只有字段、没有自身方法或生命周期的纯数据结构，包括方法参数、普通返回值、查询条件、日志描述、协议 DTO、分页结果等。
- **常见反模式**：
  - **把纯数据机械类化**：如 `class 创建学生参数` 只含 `readonly` 字段和构造赋值，应退化为 `type`。
  - **把单次调用包装成伪实体**：如 `new 订单确认执行(订单值, 参数).运行()`，若该过程无独立身份、状态和生命周期，应直接作为 `订单值.确认(参数)` 方法。
  - **为消灭自由函数建立静态工具类**：如 `class 错误工具 { static 格式化(...) }`，既无实例外延也无对象状态，应直接使用顶层函数。

## 封装与自治：每个类都是自洽的小系统

类必须独立维护内部一致性，从结构上阻止调用者以未预期的方式制造非法状态：

- **属性默认私有**：不默认暴露字段或机械提供 getter/setter；只公开外界真正需要的有限领域方法（如 `班级` 不暴露可变数组 `班级值.学生们.push(...)`，而提供 `接收学生`、`移出学生` 以维护容量与查重规则）。查询方法不得泄漏可变的内部状态引用。
- **构造后立即有效（Fail-Fast）**：构造函数是实体进入系统的第一道边界，必须校验并拒绝非法初始值。禁止先创建不完整对象再依赖调用者调用 `初始化()` 或 `检查是否合法()`。
- **修改方法守住状态迁移**：每次状态修改都必须校验输入并维持不变量。
- **通过公共语义协作**：对象之间只调用对方公开的领域方法（如订单结算调用 `订单项.获得小计()` 与 `金额.加上(另一个金额)`），不直接耦合对方的内部结构。

```ts
class 玩家 {
  private 生命值: number

  public constructor(初始生命值: number) {
    if (初始生命值 < 0) throw new Error('玩家生命值不能为负数')
    this.生命值 = 初始生命值
  }

  public 受到伤害(伤害值: number): void {
    if (伤害值 < 0) throw new Error('伤害值不能为负数')
    this.生命值 = Math.max(0, this.生命值 - 伤害值)
  }

  public 治疗(恢复值: number): void {
    if (恢复值 <= 0) throw new Error('恢复值必须为正数')
    this.生命值 += 恢复值
  }

  public 获得生命值(): number {
    return this.生命值
  }
}
```

## 类之间的关系与拆分原则

类之间的结构关系严格收敛为两种：**继承（`is-a`）**与**组合（广义 `has-a`）**。

### 1. 继承表达本体延续（`is-a`）

- 仅当“子类是一种特殊的父类（`子类外延 ⊆ 父类外延`）”在领域语义上自然成立时才使用继承或实现（如 `研究生 extends 学生`、`银行卡支付 extends 支付`、`定时任务 extends 任务`）。
- **严禁仅为了复用代码而继承**：如 `订单 extends 日志工具`、`用户仓储 extends 重试器` 均属滥用，应改用组合或工具函数。

### 2. 组合表达概念协作（广义 `has-a`）

- 一个概念通过私有属性持有、包含或引用另一个概念，并在自身行为中协调它们（如 `班级` 持有 `学生[]`，`订单` 组合 `订单项`、`支付` 与 `发货单`）。
- **跨概念协同**：当多个独立概念需要协同工作时，不要默认建立外部 `Manager` 或 `Service` 去操纵它们，而应寻找能够真实包含它们的**整体概念、关系概念或过程概念**：
  - _关系概念示例_：`学生` 与 `课程` 之间的选课若具有选课时间、状态和退课操作，应建立真实概念 `选课`。
  - _过程概念示例_：简单上传只是一个函数；但支持分片、暂停、恢复和过期后，应建立真实概念 `上传会话`。
  - _生命周期判定_：若“授权”只是简单引用，用组合即可；若具有授予人、有效期和撤销记录，则建立 `授权` 类。同理，任务运行若需被查询、恢复和重试，才建立 `任务执行` 类，否则运行描述用 `type`。

### 3. 类过长时如何拆分

类过长通常意味着混入了多个可独立成立的概念。拆分只能依据本体关系，不能按行数随意切文件：

- **沿组合拆出子概念**：如从复杂的 `订单` 中识别出独立的 `订单项`、`收货地址`、`价格明细`、`支付`、`发货单`，由 `订单` 组合协调。
- **沿继承拆出特殊化子类**：如将 `支付` 拆分为 `银行卡支付`、`余额支付`、`线下支付`。
- **无法拆出真实概念时不强拆**：若只是单一概念内部实现复杂，使用私有方法整理即可，**严禁**生造 `订单工具`、`订单辅助器（Helper）`、`状态执行器（Executor）`、`业务上下文（Context）` 等无本体含义的伪概念。

## 类头注释：显式声明概念本体

类定义完成后，必须在类声明上方编写文档注释，把该概念在问题世界中的定位直接交代清楚。这段注释既是给阅读者的领域导览，也是检验建模是否成立的试金石——如果连一段顺畅的类头注释都写不出来，往往说明概念边界尚未想清楚，或者它根本不该建为类。

在本项目的建模体系下，既然建成了 `class` 而非退化为 `type`，它就必然同时具备概念内涵与伴随操作。因此类头注释应当包含以下三项基本内容（其他内容按实际情况自然展开）：

- **它是什么**（概念定位）：说明该类在**当前系统的问题空间**中是什么（只讲它在当前系统里的角色定位，不要背诵现实世界的百科定义）。
- **它里面有什么**（概念内涵）：高层概括它包含哪些核心信息或由哪些子概念组成，与“它是什么”共同勾勒出概念的内涵。
- **它能做什么**（伴随操作）：高层概括它对外提供什么能力或支持什么操作（即类的方法；若无自身方法则早已退化为 `type`）。

编写时应使用**自然、概括的语言**，不要死板复刻“它持有……它能够……”之类的固定句式（可用“包含”“由……组成”“记录了”“负责”“支持”等自然表述），同时避免把内部字段和方法名逐一罗列成“报菜名”，也不要把具体的校验规则或内部实现细节写进注释：

```ts
/**
 * 班级是学籍管理系统中用来归组管理学生的单位。
 * 里面包含班级自身的基本信息和当前归属该班级的学生。
 * 可以通过它办理学生的转入、转出，或者查看班级的人数情况。
 */
export class 班级 { ... }

/**
 * 上传会话代表一次大文件分片上传的过程。
 * 当中记录了待上传文件的信息以及目前已收到的分片进度。
 * 主要负责接收后续分片、控制上传的暂停与继续，并在结束时完成文件合并或取消上传。
 */
export class 上传会话 { ... }
```

## 建模与代码审查自检清单

新增或审查类时，必须满足以下全部准入与自检条件：

1. **内涵、外延与类头注释**：能用领域语言清楚定义它的必要属性与不变量，能举出外延中的具体实例，且已在类头注释中交代清楚“它是什么、里面有什么、能做什么”。
2. **操作内聚**：伴随它存在的领域行为均已放入类方法中，未散落在外部函数、`Service` 或 `Manager` 中。
3. **非纯数据或临时过程**：它**不是**单次调用的参数、普通返回值、查询条件或无状态过程（若是，应退化为 `type` 或方法/函数）。
4. **边界自洽**：属性默认 `private`；构造函数拒绝非法初始值（构造即有效）；修改方法守住状态迁移后的不变量；查询方法不泄漏可变内部引用。
5. **关系纯正**：继承严格满足 `is-a`；跨概念协同与大类拆分由真实的整体/关系/过程概念承载，未生造 `Helper / Manager / Executor / Context` 等伪概念。
