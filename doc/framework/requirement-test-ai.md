# AI 需求测试提示词

你在为本项目编写需求测试。你的任务是把用户给出的业务需求变成可重复执行的流程，并留下足以判断每个验收点是否通过的证据。可以直接编写用例，也可以通过测试开发套件的 MCP 操作、记录和导出。测试入口、运行选项和 MCP 启动方法见[测试文档](testing.md)。

尽量使用子智能体，把可独立完成的验收点分析、用例编写或结果核对分派出去，由主智能体汇总结果。

## 先确定要证明什么

- 把需求拆成可观察的验收点。写清前置条件、谁做什么、预期看到什么。例如「未登录的访客用已被占用的用户名注册后，页面显示用户名已存在，且没有新增账号」。
- 区分需求明确要求的行为和你从当前实现中观察到的行为。实际结果与需求不符时，保留断言并报告差异。需要人工判断的验收点标为人工，并写清楚人工要看什么。
- 每条流程应能独立运行。准备阶段可以在测试库构造所需数据，待验证的业务动作走实际的 UI、接口或命令。查询数据库可以用来核对业务结果。

## 按业务动作组织步骤

- 需求、流程和步骤用简短的中文命名。把同一目的的连续动作放在一起，例如打开登录页、填写凭据并提交可以合成「管理员登录」。把有独立验收意义的检查写成观察，例如「确认重名注册被拒绝」。
- 用能直接证明结果的断言。页面异步更新时，等待具体提示、目标元素或地址变化。整页快照适合探索页面，回放时优先断言与验收点有关的内容。若要证明数据已落库，就查询对应记录并检查关键字段。
- 用「测试思路」说明准备怎么验证、什么结果算通过。用「结论补充」交代覆盖范围或待人工核对的事项，报告会根据实际运行结果给出执行结论。

## 直接编写用例时

- 把用例放在 `test/requirement/`，可以按业务建子目录，各层的 `helper/` 用于放辅助代码。可参考[强类型表单测试](../../test/requirement/typed-form.ts)和[管理员用户管理测试](../../test/requirement/user-management.ts)。
- 默认导出无参构造的 `需求测试` 子类，构造时登记需求、流程和是否使用测试服务。`准备数据(工具)` 返回业务数据，框架会把它与工具一起放入流程上下文。
- 调用 `工具.数据库.查询(SQL, 参数, 报告列)` 时，用参数传入业务值。需要在报告里展示查询结果时，只把可公开的字段列入 `报告列`。
- 每次提交步骤附件会生成一页，数组里可以混合文本和图片。截图和文字解释同一个结果时，用 `提交附件(附件们, { 并入上一组: true })` 把内容追加到同一步骤的上一页。没有上一页时照常新建一页。

## 使用 MCP 录制时

- 先实际执行待验收的业务流程，再从记录里挑出回放需要的操作。保留必要的准备、操作、等待和断言，去掉误点、重复查询和仅用于定位控件的探索操作。整理完仍应保留实际执行顺序。
- 需要解释为什么做某个检查时，用 `record_note` 写一段随步骤展示的决策说明。例如「保存后弹窗已关闭，再查一次数据库确认数据已落库」。
- 用 `record_add_assertion` 断言工具结果中的具体字段，导出时把来源操作也选进去。若断言文字用于解释同一步骤的上一份截图或证据，可以设置 `mergeWithPreviousAttachmentGroup: true`。
- 用 `record_export` 的 `steps` 给操作分组，并在 `scenarioApproach` 里写清测试思路。需要说明覆盖范围或人工确认事项时，填写 `conclusionNotes`。

## 回放并交付

编写或导出后，运行对应流程并查看报告。测试开发套件与需求测试共用测试库，回放前先退出测试开发套件，并与使用同一数据库的其他测试串行执行。

```sh
npm run test:requirement -- --scenario "流程名称" --auto
```

交付时给出用例路径、运行结果和报告路径。若流程失败，指出失败的步骤、预期与实际。若没有回放或仍需人工验收，明确写出哪些结果待确认。
