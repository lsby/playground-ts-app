# AI 需求测试提示词

你在为本项目验证业务需求并生成可重复执行的需求测试。你的核心工作流是：**先与用户讨论敲定需求与验收点并落盘需求描述文件 ➔ 启动测试环境通过 MCP 边探索验证边修复代码问题 ➔ 跑通后修剪操作记录并机械转换为流程实现文件 ➔ 回放验证后向用户交付体验命令**。测试入口、运行选项和 MCP 启动方法见[测试文档](testing.md)。

当需求包含多个可独立推进的模块或流程时，可以使用子智能体分派独立的分析、验证或结果核对任务，由主智能体汇总。

## 阶段一：拆解验收点并与用户对齐，先写需求描述文件

1. **拆解并与用户讨论验收点**
   - 收到用户的测试或验收请求后，不要直接编写具体的测试操作代码。
   - 先把业务需求拆成具体、可观察的**验收点**。每个验收点用简短的名称概括结果，在描述中写清前置条件、谁做什么、预期看到什么（如「未登录的访客用已被占用的用户名注册后，页面显示用户名已存在，且数据库没有新增账号」）。
   - 将拆解出的需求与验收点列表呈现给用户，与用户讨论确认。
2. **落盘 `.requirement.ts` 需求描述文件**
   - 与用户达成一致后，先创建 `test/requirement/<name>/<name>.requirement.ts`（目录名与文件名均使用英文小写短横线命名）。
   - 此时**只写需求与验收点定义，不写任何具体测试步骤**。固定导出 `验收点们` 和 `业务需求`，例如：

```ts
import { 需求, 验收点 } from '../../../src/model/test-requirement'

export let 验收点们 = {
  重名被拒绝: new 验收点({ 名称: '重名被拒绝', 描述: '重名提交会显示已存在提示，且不会新增账号。' }),
  注册成功: new 验收点({ 名称: '注册成功', 描述: '使用新用户名提交后成功创建账号。' }),
}

export let 业务需求 = new 需求({
  名称: '访客注册',
  描述: '访客可以注册新账号，用户名必须唯一。',
  验收点们: Object.values(验收点们),
})
```

## 阶段二：启动测试环境，通过 MCP 交互式验证与自主排障

需求描述文件落盘后，启动或连接测试开发套件的 MCP（可通过 `test_info` 获取当前测试前端、后端地址与记录路径），使用 `browser_*`、`database_query`、`backend_logs` 等工具在真实系统中逐项操作并验证验收点。

在测试过程中发现实际表现与验收点不符时，按问题性质自主决策：

- **小问题或局部 Bug（自行修复并决定续测还是重测）**
  - 直接定位并修改业务源码。测试开发套件具备前端热更新与后端自动重启能力，修改会立即反映到测试环境。
  - 改完代码后，根据该问题是否污染了当前测试现场做出判断：
    - **可继续往下测**：如果只是界面文案、局部交互或未破坏前置数据的小问题，刷新或留在当前现场继续验证后续步骤即可（刚才失败或多余的操作可在阶段三修剪时用 `record_remove` 删掉）。
    - **需要从头重测**：如果问题已经弄脏了数据库状态或破坏了前置流程，调用 `database_reset` 停止后端、重置 Web 测试数据库并重启后端，再重新打开浏览器从头验证。`database_reset` 默认保留已有操作记录（便于保留同一需求下前面已跑通的其他流程记录）；若要彻底丢弃当前全部记录重新开始，传入 `clearRecord: true`。
- **致命问题或需求分歧（立即停下并向用户报告）**
  - 如果发现系统核心设计与需求存在根本冲突、需求本身存在歧义、或需要重大破坏性修改才能实现，**立即停止探索**。
  - 向用户如实报告观察到的现场现象、日志/数据库证据以及冲突原因，征询用户的意见后再决定下一步，不要盲目硬改。

## 阶段三：修剪操作记录并机械转换为测试代码

当业务流程在 MCP 中完整跑通、所有目标验收点均得到验证后，将探索过程整理并机械转换为正式的需求测试实现文件：

1. **审阅与修剪操作记录**

- 调用 `record_list` 和 `record_get` 查看刚才执行过程中的操作记录。
- 调用 `record_remove` 删掉误点、报错重试前的废操作、重复查询以及仅用于定位控件的整页探索快照；必要时用 `record_move` 调整顺序，仅保留回放所需的准备、操作、等待和断言，并保持实际执行顺序。
- 页面异步更新时，回放中应保留等待具体提示、目标元素或地址变化的 `browser_wait` / `browser_wait_url`；要证明数据已落库，应保留查询对应记录的 `database_query`。

2. **补充决策说明与结果断言**

- 需要解释为什么做某个检查时，用 `record_note` 填写 `decision`（例如「保存后弹窗已关闭，再查一次数据库确认数据已落库」），导出后会在报告步骤中展示。
- 用 `record_add_assertion` 断言工具结果中的具体字段（如数据库查询返回的行数或字段值），导出时必须把该断言的来源操作（`sourceId`）也一并选入。若断言文字用于解释同一步骤的上一份截图或证据，可设置 `mergeWithPreviousAttachmentGroup: true`。

3. **调用 `record_export` 机械转换落盘**

- 用 `record_export` 的 `steps` 将选中的操作和断言 ID 按业务动作分组，使用简短中文命名流程（`scenarioName`）和每个步骤（`title`）：
  - 把同一业务目的的连续动作合成一个步骤（例如打开登录页、填写凭据、提交并等待跳转合成「管理员登录」）。
  - 把有独立验收意义的检查单独分为只含检查/断言的观察步骤（例如「确认重名注册被拒绝」），导出流程至少需要一个观察步骤。
  - 在 `scenarioApproach` 中写清测试思路（准备怎么验证、什么结果算通过），需要交代覆盖范围或特殊说明时填写 `conclusionNotes`。
- 每次调用 `record_export` 导出一条流程，传入 `requirementFile`（如 `visitor-registration.requirement.ts`）和 `fileName`（如 `reject-duplicate-registration.ts`），机械转换工具会在 `test/requirement/<name>/` 下生成完整的流程实现文件（同名文件已存在时会拒绝覆盖）。
- 当需求包含多个验收点时，必须传入 `acceptanceCriteriaKeys`，填写 `验收点们` 中当前流程真正证明的键。验收点的名称用于报告展示。若一个需求由多条独立流程覆盖不同验收点，可分多次导出到同目录下的不同 `.ts` 文件。
- 若手动修改了已被 MCP 加载过的需求描述或流程文件，需先重启测试开发套件再执行导出。

## 阶段四：回放验证并交付体验命令

生成流程实现文件后，**先关闭测试开发套件**（测试开发套件与需求测试共用同一个 Web 测试库，回放前必须释放数据库锁，并与使用同一数据库的其他测试串行执行），然后运行回放验证：

```sh
npm run test:requirement -- --scenario "流程名称" --auto
```

若该需求的全部验收点均已导出对应流程，也可按需求名称或全量运行验证。

验证通过后，通知用户任务已完成，并在回复中交付：

1. 生成的需求描述文件与流程实现文件路径，以及运行报告路径。
2. 供用户亲自运行和可视化体验该需求测试的命令（同时给出自动模式 `--auto` 与带可见浏览器动画引导的演示模式 `--demo`）：

   ```sh
   npm run test:requirement -- --scenario "流程名称" --demo
   npm run test:requirement -- --scenario "流程名称" --auto
   ```

## 附：直接编写或手动维护流程代码时的约定

若无需通过 MCP 录制、而是直接手写或微调 `test/requirement/<name>/<flow-name>.ts`（可参考强类型表单的[需求定义](../../test/requirement/typed-form/typed-form.requirement.ts)与[流程实现](../../test/requirement/typed-form/typed-form.ts)，以及[管理员用户管理测试](../../test/requirement/user-management/user-management.ts)）：

- 流程文件从同目录的 `<name>.requirement.ts` 导入 `业务需求` 和 `验收点们`，默认导出无参构造的 `需求测试` 子类，构造时登记需求、流程和是否使用测试服务。`准备数据(工具)` 返回业务数据，框架会将其与工具一起放入流程上下文。
- 调用 `工具.数据库.查询(SQL, 参数, 报告列)` 时，用参数传入业务值。需要在报告里展示查询结果时，只把可公开的字段列入 `报告列`。
- 每次提交步骤附件会生成一页，数组里可以混合文本和图片。截图和文字解释同一个结果时，用 `提交附件(附件们, { 并入上一组: true })` 把内容追加到同一步骤的上一页。
