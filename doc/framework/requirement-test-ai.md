# AI 需求测试提示词

你在为本项目验证业务需求并生成可重复执行的需求测试。
可能的场景包括新需求的实现、已有实现的验收、已有缺陷的修复，以及因项目迭代导致旧测试失效时的修正。
系统为你提供了一套MCP服务，你可以用这套服务方便地操作系统，同时你也可以看到当前系统的所有代码，进行任意的修改。
你的核心工作流是：**先与用户讨论敲定需求与验收点并落盘需求描述文件 ➔ 启动测试环境通过 MCP 交互验证，发现问题当场修改后接着往下走 ➔ 审阅并导出流程实现文件**。
测试入口、运行选项和 MCP 启动方法见[测试文档](testing.md)。

## 这套框架要解决什么

传统做法是让 AI 直接写端到端测试脚本：先凭想象写好每一步，跑一遍，哪里坏了就猜原因、改脚本、从头再跑。这条路的问题不在于 AI 写得不好，而在于**它是盲的**：AI 在脚本写成之前从没真正"看"过应用，只能靠一次次失败去摸应用长什么样。结果是测试越补越脆，大量时间花在重跑上，而真正的缺陷常常被等待、重试、绕路这些补丁盖掉。

这个框架把顺序倒过来：**先像人一样真实地使用应用，再由框架把使用过程整理成测试。** 智能体在实时环境里做一步、看一步，根据看到的结果决定下一步；碰到问题就在现场弄清楚、当场解决，然后接着往下走。框架负责记录每一步做了什么、看到了什么，最后从这份记录生成可重复执行的流程。测试是使用过程的产物，而不是事先写好、再拿去碰运气的东西。

所以，判断自己有没有走偏，只需要问一句：**我现在是在"看着应用操作"，还是在"对着脚本调试"？** 如果你发现自己在改流程代码、杀掉应用、从头重跑，再根据失败的步骤猜原因、接着改，那就是又回到了这个框架想要取代的老路上，应该停下来，回到实时环境，去看应用本身。

几条由此而来的提醒：

- 每次操作的返回结果就是你的眼睛，先看清再决定下一步。结果不符合预期时，先找出真正的原因，不要靠加等待、加重试把它掩过去。
- 问题解决后从当前步骤继续，不从头来。
- 流程由录制生成。回放失败也回到实时环境去处理，而不是直接去改生成的代码。

当需求包含多个可独立推进的模块或流程时，可以使用子智能体分派独立的分析、验证或结果核对任务，由主智能体汇总。

## 浏览器资源与串行执行

- 整个任务同时最多保留一个无头浏览器会话，主智能体、子智能体和额外启动的 CLI 共用这个限制。浏览器场景必须逐个串行执行，由一个测试执行方操作；不得用多个智能体、终端或测试套件同时打开浏览器。
- 打开浏览器前用 `browser_list` 确认当前会话；可以继续使用当前会话时直接复用。需要切换账号、隔离登录状态或开始下一条独立流程时，先用 `browser_close` 关闭旧会话并确认成功，再打开新会话。不得把旧页面留在后台等待以后再测，动画、3D 和视频页面尤其如此。
- 每条流程结束后立即关闭浏览器会话，保存录制与证据后再处理下一条。正式回放也必须串行执行，在流程结束或异常退出时释放浏览器；手动维护流程代码时用 `finally` 确保关闭。只读分析可以并行，但不得另开浏览器。
- 同时只保留一套测试开发环境。启动正式回放前先关闭开发套件并确认退出；测试结束、暂停或用户反馈电脑卡顿时，及时关闭本任务的浏览器、测试服务和编译监听。只清理本任务创建的进程，不按进程名称批量结束用户自己的浏览器或其他应用。Chromium 自带的渲染、图形等子进程属于同一浏览器，不通过强杀这些子进程限制数量。

框架自动模式会跨进程限制一个无头浏览器，冲突时按报错找到占用会话并正常关闭，不结束其他任务的进程。录制操作返回的 `replay.supported` 应在整理时检查；画面稳定和截图只作证据，异步结果仍要录下显式等待与检查。目标有多个匹配时用 `within` 或唯一角色收窄，不靠随手取第一个绕过。

修改已经加载的需求流程或辅助模块后，重启测试进程或开发套件再回放；框架会拒绝继续执行缓存的旧源码。补测可用 `--retry-failed <report.json> --list` 先确认范围，执行后交付原报告、本次报告与 `combined.html` 汇总，分别说明产品现象、脚本问题和环境问题。

## 阶段一：与用户确认验收点

1. **拆解并与用户讨论验收点**
   - 用户可能会提出一个新功能的想法，或者一个已有功能的验收，或者一个已有缺陷的修复，亦或是因项目迭代需要修正已失效的旧需求测试等意图。
   - 你需要先把业务需求拆成具体、可观察的**验收点**。每个验收点用简短的名称概括结果，在描述中写清前置条件、谁做什么、预期看到什么（如「未登录的访客用已被占用的用户名注册后，页面显示用户名已存在，且数据库没有新增账号」）。
   - 验收点按需求规模定，够用即可：简单功能一般 2～4 个。只写用户能感知的核心结果和关键边界；同一结果的不同输入（如选普通项、填其他、跳过）合成一个验收点，字段级的细节放进断言，不单独成点。先给用户一份最小清单，用户要求再加。
   - 与用户确认需要验证的条件和交付范围。如果有相似的需求或需求点，可以考虑修改已有的(但不要尝试复用需求点的测试逻辑-即流程，因为流程是自动生成的)，而不是每次都创建新的。
2. **按需更新需求描述文件**
   - 需求描述放在 `test/requirement/<name>/index.requirement.ts`，也可用多层目录分组，如 `test/requirement/shopping/checkout/index.requirement.ts`。各层使用英文小写短横线命名。导出时 `requirementDirectory` 传相对于 `test/requirement/` 的路径，如 `shopping/checkout`。
   - 此时**只写需求与验收点定义，不写任何具体测试步骤**。固定导出 `验收点们` 和 `业务需求`，例如：

```ts
import { 需求, 验收点 } from '../../../src/model/test-requirement'

export let 验收点们 = {
  重名被拒绝: new 验收点({ 名称: '重名被拒绝', 描述: '重名提交会显示已存在提示，且不会新增账号。' }),
  注册成功: new 验收点({ 名称: '注册成功', 描述: '使用新用户名提交后成功创建账号。' }),
}

export let 业务需求 = new 需求({
  名称: '访客注册',
  描述: '访客可以注册新账号，用户名必须唯一。',
  验收点们: Object.values(验收点们),
})
```

## 阶段二：按任务实施并验证

确认验收点后，按任务从对应的步骤开始。

- **实现新功能**。按已确认的验收点实现功能，再从用户正常使用的入口验证。
- **验收已有功能**。逐项验证验收点，记录实际结果。
- **修复缺陷**。先按触发条件尽量复现，记录实际结果。修完后用相同条件再验证，并检查受影响的行为。
- **修正失效测试**。先运行旧测试定位失败步骤与原因。若是交互细节、界面元素或断言因实现变动而过时，通过 MCP 重新录制或手动维护流程代码进行修复；若涉及业务规则变更，先与用户确认变更后的验收点再同步更新。

需要交互验证时，按[启动和连接说明](testing.md#启动和连接)进入测试环境，用 [MCP 工具](testing.md#工具与录制)操作并收集证据。

动手录制前先规划流程：流程越少越好，一条流程尽量证明多个验收点，能在同一账号、同一路径上连着验证的放进同一条；简单需求一般 1～3 条流程。需要测试数据时，先 `database_reset`，用 `database_schema` 查表结构，再用 `database_execute` 在现场造数据，用 `database_query` 核对；能通过界面或接口自然产生的数据优先走界面，SQL 用于界面做不到的，比如历史天数、特殊状态。造数据的写入会进录制，导出时自动生成流程的 `初始化`，不需要手写。写入必须确定：不用随机值，不用当前时间造关键数据，日期按业务日推算，回放才与录制一致。`database_reset` 本身不进录制，回放又总从清库开始，所以造数据前先重置，重置之前录下的旧操作用 `record_remove` 排除。

通过 MCP 操作浏览器、调用接口或查询数据库时，测试环境会自动保存操作、结果和可用证据，这份现场记录叫作录制。一条流程先完整走通，结束后再回看这一段，选出正式测试需要重做的操作，整理成回放草稿，不要每做一步就停下来整理。排除误点或失败尝试后，原始记录仍可查阅。

走流程时留意操作不便、界面体验不佳和其他可改进的地方。把建议关联到当时的操作，写清实际现象和影响，有明确想法时可补上改进方向。建议单独出现在报告里，验收按与用户确认的条件判断。

**边测试边修改**：用需求测试修 bug 或做功能时，开着测试环境一步步走流程。走到哪一步发现问题，就当场改代码，然后接着往下走，不要先把代码全写完再另找人录制验收，也不要每走一步就停下来整理。

- 多个智能体协作时，测试和改代码分给两个常驻的智能体，由主智能体调度和验收（转交问题与结果，亲自看关键画面）。双方不需要知道对方的过程，只交接结果：测试方交「哪一步、预期、实际、截图路径」；改代码方交「已修好，改的是前端还是原生（决定要不要重建）、影响哪些页面（决定从哪一步重测）」。智能体完成一轮后停下等待，上下文保留，下一轮继续用同一个。
- 测试方测试时几乎只通过 MCP 操作和查看设备（含截图、`database_query` 查库），不边测边写流程代码，不中途跑回放，不读业务源码找原因，表结构只用 `database_schema` 查看，不读源码文件；现象不对就把该步自动保存的画面路径（返回值的 `artifacts`）附在问题单里，看不清时再自己截一张。查库必须用 `database_query`，直接用数据库命令行查询不会进入录制。必须先把测试 MCP 挂到客户端（登记方法见测试文档），不要用 curl、脚本或循环绕过客户端直接调用测试 MCP，也不要把多个界面操作串成一次批量执行。
- 一条流程在 MCP 里完整走通后，才用录制工具回看整理：`record_list`、`record_get`、`record_review` 查看，`record_remove` 去掉误点和失败尝试，`record_group` 按业务步骤分组，`record_note` 加备注，`record_add_assertion` 补断言，`record_add_suggestion` 记建议，最后 `record_export` 导出。所有流程导出后，把这次新写或改过的流程一起回放一次（见「回放与交付」）。手写流程代码只用于 MCP 做不到的部分。

- 小改动（文案、样式、一两行逻辑）改完直接继续，不用从头重录。
- 只有改动影响了前面已经走过的步骤（比如改了它依赖的数据或页面结构），才从受影响的那一步重走。
- 流程全部走通后再导出，导出后回放一次确认通过；回放才是最终证明。

**看清再操作**：等页面状态一律按条件等，不用固定秒数的 sleep 去猜。

- 等待用 `browser_wait`，等某个文字或选择器出现。构建等待原命令完成，服务启动等待约定的就绪日志或事件，并设上限时间；超时就停下查原因，不盲目重启，也不反复加长等待。
- 浏览器界面动作默认共用多帧采样、灰度比较和选帧，最多六秒、最多三张图片；选中帧按约 200 万像素目标及 CSS 逻辑尺寸的清晰度下限等比例缩放，小图不放大，再以 WebP 质量 85 编码，直接随 MCP 工具结果返回，不做自动 OCR。观察只辅助判断下一步，不导出为回放等待。异步弹窗应明确等待出现，关闭后再等待消失；单独等待隐藏可能在弹窗尚未出现时提前通过。页面就绪使用 `browser_wait` 或 `browser_wait_url`，这些条件会原样进入回放，采样返回和画面静止都不替代它们。
- 点击新手教学、引导里的目标前，先用 `browser_wait` 等该步的提示文字出现，再点目标。教学步骤切换的瞬间目标元素会短暂点不动，不等提示文字就点会偶发失败，也不要靠加长固定等待绕过去。录制数据里没有可靠的「点击前页面文字」（观察只返回截图，不做自动 OCR），所以导出不能自动补这一步，需要测试方在录制时自己写进流程。
- 验证慢响应离开时，可通过 `browser_request_hold` 挂起一次精确匹配的测试后端响应，等 `browser_request_wait` 确认真实响应已取得后再离开页面，随后释放响应。释放后还要等待业务已经消费结果的可见信号，再核对页面和历史；请求结束本身不能替代业务完成条件。挂起不会撤销后端副作用，也不会替换响应，准备时应使用允许执行的合成账号和数据。
- 浏览器返回选中帧的采样时间，图片四周的刻度数字就是操作坐标（CSS 视口像素），不需要换算；证据图保持干净不带刻度；同时返回 `settled`、`durationMs`，有前置基准时返回 `changed`。坐标点击只是兜底，优先用按文字或元素定位的点击工具。坐标点击在录制时会被自动识别：框架在点击前找出落点元素并生成唯一定位，导出时变成按元素点击（先等元素出现再点）；动作前后页面地址变了，导出时自动在动作后等地址；新导出的代码不再生成等待画面稳定。识别不出可用定位（Canvas、空白）时，改用点击前截图裁出的图片模板，回放等图片出现再点，纯色区域才退回原坐标，并自动记一条建议。工具返回的 `locator` 字段会说明识别结果。看到「建议加 aria-label」的建议时，应该给前端元素补标签（或唯一的 id、data 属性），不要靠加等待绕过去。详见[回放等待](testing.md#操作后的图片观察与回放等待)。观察失败的 `observationError` 不改变已经成功的动作结果，先检查错误和证据，不重复点击。
- 直接查看工具返回的图片，根据画面决定下一步。图片包含时间顺序，最终帧有明确说明；需要准确定位时按需查看页面结构。画面过时或需要最新状态时，再调用 `browser_screenshot`；已有证据也可按需从 `artifacts[].path` 打开，不要求每步额外截图或读文件。
- 网页结构（`browser_inspect_page`）适合找定位、查状态，同样按需使用；它看不出排版、遮挡、错误页和误导性提示，这些要靠返回图片判断。
- 使用界面工具时，框架会在步骤结束后尝试保存画面，成功保存的文件路径放在返回值的 `artifacts` 中。附件为空或有取证错误时，按实际需要调用截图工具。交问题单和交付时直接引用已有图片路径，每个用一句话说明看到了什么，不必为留证据专门截图。

在测试过程中发现实际表现与验收点不符时，按问题性质自主决策：

- **小问题或局部 Bug（自行修复并决定续测还是重测）**
  - 直接定位并修改业务源码。测试开发套件具备前端热更新与后端自动重启能力，修改会立即反映到测试环境。
  - 改完代码后，根据该问题是否污染了当前测试现场做出判断：
    - **可继续往下测**：如果只是界面文案、局部交互或未破坏前置数据的小问题，刷新或留在当前现场继续验证后续步骤即可，把失败或多余的尝试排除出回放草稿。
    - **需要从头重测**：如果问题已经弄脏了数据库状态或破坏了前置流程，重置 Web 测试数据库和测试服务，再重新打开浏览器从头验证。重置默认保留已有操作记录，回放时选用适合本次验证的操作。
- **致命问题或需求分歧（立即停下并向用户报告）**
  - 如果发现系统核心设计与需求存在根本冲突、需求本身存在歧义、或需要重大破坏性修改才能实现，**立即停止探索**。
  - 向用户如实报告观察到的现场现象、日志/数据库证据以及冲突原因，征询用户的意见后再决定下一步，不要盲目硬改。

## 阶段三：按需更新需求测试

- 系统实现了一个操作记录器，当你调用MCP服务时，会自动记录一些操作，你也可以手动调用来记录一些操作，这些操作会在最终程序化的导出为需求测试的代码，你也可以在任何时候查看这些操作来进行维护或者备注等。
- 推荐当一条流程整体跑通后，再通过MCP工具来回看这个流程的具体操作，如果存在无意义的操作，可以编辑，如果操作过于复杂，可以加入备注。
- 推荐当业务流程在 MCP 中结束后，再做最后一次检查，然后导出正式的需求测试实现文件。

1. **审阅步骤与证据**

- 确认草稿只保留回放需要的准备、操作和检查，顺序能从干净的测试环境重现结果。若验证时在 MCP 之外准备了数据，可以补记当时做过什么，并把可重复的准备逻辑写入测试流程。
- 把同一业务目的的连续动作合成一个步骤，例如打开登录页、填写凭据和提交可以合成「管理员登录」。建议随关联操作进入报告。

2. **补充说明与验收检查**

- 需要解释为什么做某组操作时，可以为整组加一条备注。导出后在对应步骤中展示。
- 将验收检查单独分为观察步骤，用断言或明确的等待目标核对结果。页面异步更新时，等待验收点对应的提示、元素或地址。只把与用户确认的条件写成验收断言。每个验收点核对 1～2 个最能说明结果的值（如关键提示、关键字段），不逐字段核对。

3. **导出流程**

- 流程文件放在对应的需求目录。为流程和步骤起简短的业务名称，说明怎么验证、什么结果算通过，并选定该流程实际证明的验收点。每次导出一条流程，生成文件与对应的需求描述放在同一目录。
- 如果导出指出选中了失败操作、断言缺少来源或步骤顺序有误，按提示修正草稿后再导出。若手动修改了测试开发套件已经读取的需求描述或流程文件，先重启套件。

4. **回放与交付**

- 所有流程导出后，只回放这次新写或改过的流程，重复传入 `--scenario` 一次跑完；这次回放就是最终证明，不再按需求整体回放。同一处失败连续两次仍不过，停下来向用户报告现象和证据，不要反复调。
- 完成后把框架生成的报告路径（`test-outputs/requirement-report/<运行号>/index.html`）交给用户，回复里只写结论和发现的问题，不另写报告。

## 附：直接编写或手动维护流程代码时的约定

若无需通过 MCP 录制、直接手写或维护 `test/requirement/<name>/<flow-name>.ts` 时，遵循以下约定。

- 流程文件从同目录的 `index.requirement.ts` 导入 `业务需求` 和 `验收点们`，默认导出无参构造的 `需求测试` 子类，构造时登记需求、流程和是否使用测试服务。每条流程必须提供 `初始化` 回调，直接接收 `工具` 并返回完整的流程状态；行为和观察使用该状态。
- 每一个流程都会是一个文件。
- 调用 `工具.数据库.查询(SQL, 参数, 报告列)` 时，用参数传入业务值。需要在报告里展示查询结果时，只把可公开的字段列入 `报告列`。
- 每次提交步骤附件会生成一页，数组里可以混合文本和图片。截图和文字解释同一个结果时，用 `提交附件(附件们, { 并入上一组: true })` 把内容追加到同一步骤的上一页。
