# AI 需求测试提示词

你在为本项目验证业务需求并生成可重复执行的需求测试。你的核心工作流是：**先与用户讨论敲定需求与验收点并落盘需求描述文件 ➔ 启动测试环境通过 MCP 交互验证并按需修复问题 ➔ 审阅并导出流程实现文件 ➔ 回放验证后向用户交付体验命令**。测试入口、运行选项和 MCP 启动方法见[测试文档](testing.md)。

当需求包含多个可独立推进的模块或流程时，可以使用子智能体分派独立的分析、验证或结果核对任务，由主智能体汇总。

## 阶段一：拆解验收点并与用户对齐，先写需求描述文件

1. **拆解并与用户讨论验收点**
   - 收到用户的测试或验收请求后，不要直接编写具体的测试操作代码。
   - 先把业务需求拆成具体、可观察的**验收点**。每个验收点用简短的名称概括结果，在描述中写清前置条件、谁做什么、预期看到什么（如「未登录的访客用已被占用的用户名注册后，页面显示用户名已存在，且数据库没有新增账号」）。
   - 将拆解出的需求与验收点列表呈现给用户，与用户讨论确认。
2. **落盘 `.requirement.ts` 需求描述文件**
   - 与用户达成一致后，先创建 `test/requirement/<name>/index.requirement.ts`，其中 `<name>` 使用英文小写短横线命名。
   - 此时**只写需求与验收点定义，不写任何具体测试步骤**。固定导出 `验收点们` 和 `业务需求`，例如：

```ts
import { 需求, 验收点 } from '../../../src/model/test-requirement'

export let 验收点们 = {
  重名被拒绝: new 验收点({ 名称: '重名被拒绝', 描述: '重名提交会显示已存在提示，且不会新增账号。' }),
  注册成功: new 验收点({ 名称: '注册成功', 描述: '使用新用户名提交后成功创建账号。' }),
}

export let 业务需求 = new 需求({
  名称: '访客注册',
  描述: '访客可以注册新账号，用户名必须唯一。',
  验收点们: Object.values(验收点们),
})
```

## 阶段二：启动测试环境，通过 MCP 交互式验证与自主排障

需求描述文件落盘后，按[启动和连接说明](testing.md#启动和连接)进入测试环境，用 [MCP 工具](testing.md#工具与录制)逐项验证验收点。

通过 MCP 操作浏览器、调用接口或查询数据库时，测试环境会自动保存操作、结果和可用证据，这份现场记录叫作录制。每完成一个业务动作或检查，回看刚才这一段，选出正式测试需要重做的操作，整理成回放草稿。排除误点或失败尝试后，原始记录仍可查阅。

走流程时留意操作不便、界面体验不佳和其他可改进的地方。把建议关联到当时的操作，写清实际现象和影响，有明确想法时可补上改进方向。建议单独出现在报告里，验收按与用户确认的条件判断。

在测试过程中发现实际表现与验收点不符时，按问题性质自主决策：

- **小问题或局部 Bug（自行修复并决定续测还是重测）**
  - 直接定位并修改业务源码。测试开发套件具备前端热更新与后端自动重启能力，修改会立即反映到测试环境。
  - 改完代码后，根据该问题是否污染了当前测试现场做出判断：
    - **可继续往下测**：如果只是界面文案、局部交互或未破坏前置数据的小问题，刷新或留在当前现场继续验证后续步骤即可，把失败或多余的尝试排除出回放草稿。
    - **需要从头重测**：如果问题已经弄脏了数据库状态或破坏了前置流程，重置 Web 测试数据库和测试服务，再重新打开浏览器从头验证。重置默认保留已有操作记录，回放时选用适合本次验证的操作。
- **致命问题或需求分歧（立即停下并向用户报告）**
  - 如果发现系统核心设计与需求存在根本冲突、需求本身存在歧义、或需要重大破坏性修改才能实现，**立即停止探索**。
  - 向用户如实报告观察到的现场现象、日志/数据库证据以及冲突原因，征询用户的意见后再决定下一步，不要盲目硬改。

## 阶段三：审阅回放草稿并导出测试代码

当业务流程在 MCP 中完整跑通、目标验收点均得到验证后，做最后一次检查，再导出正式的需求测试实现文件。

1. **审阅步骤与证据**

- 确认草稿只保留回放需要的准备、操作和检查，顺序能从干净的测试环境重现结果。若验证时在 MCP 之外准备了数据，可以补记当时做过什么，并把可重复的准备逻辑写入测试流程。
- 把同一业务目的的连续动作合成一个步骤，例如打开登录页、填写凭据和提交可以合成「管理员登录」。建议随关联操作进入报告。

2. **补充说明与验收检查**

- 需要解释为什么做某组操作时，可以为整组加一条备注。导出后在对应步骤中展示。
- 将验收检查单独分为观察步骤，用断言或明确的等待目标核对结果。页面异步更新时，等待验收点对应的提示、元素或地址。只把与用户确认的条件写成验收断言。

3. **导出流程**

- 为流程和步骤起简短的业务名称，说明怎么验证、什么结果算通过，并选定该流程实际证明的验收点。每次导出一条流程，生成文件与对应的需求描述放在同一目录。
- 如果导出指出选中了失败操作、断言缺少来源或步骤顺序有误，按提示修正草稿后再导出。若手动修改了测试开发套件已经读取的需求描述或流程文件，先重启套件。

## 阶段四：回放验证并交付体验命令

生成流程实现文件后，按[退出说明](testing.md#退出后再回放)关闭测试开发套件，再运行回放验证：

```sh
npm run test:requirement -- --scenario "流程名称" --auto
```

若该需求的全部验收点均已导出对应流程，也可按需求名称或全量运行验证。

验证通过后，通知用户任务已完成，并在回复中交付：

1. 生成的需求描述文件与流程实现文件路径，以及运行报告路径。
2. 供用户亲自运行和可视化体验该需求测试的命令（同时给出自动模式 `--auto` 与带可见浏览器动画引导的演示模式 `--demo`）：

   ```sh
   npm run test:requirement -- --scenario "流程名称" --demo
   npm run test:requirement -- --scenario "流程名称" --auto
   ```

## 附：直接编写或手动维护流程代码时的约定

若无需通过 MCP 录制、而是直接手写或微调 `test/requirement/<name>/<flow-name>.ts`（可参考已有需求测试）：

- 流程文件从同目录的 `index.requirement.ts` 导入 `业务需求` 和 `验收点们`，默认导出无参构造的 `需求测试` 子类，构造时登记需求、流程和是否使用测试服务。`准备数据(工具)` 返回业务数据，框架会将其与工具一起放入流程上下文。
- 调用 `工具.数据库.查询(SQL, 参数, 报告列)` 时，用参数传入业务值。需要在报告里展示查询结果时，只把可公开的字段列入 `报告列`。
- 每次提交步骤附件会生成一页，数组里可以混合文本和图片。截图和文字解释同一个结果时，用 `提交附件(附件们, { 并入上一组: true })` 把内容追加到同一步骤的上一页。
