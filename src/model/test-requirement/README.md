# 需求测试模型设计

这个模块提供一种从需求出发组织测试的方式。它不把单元测试、集成测试、端到端测试当作模型的中心，因为这些名称描述的是技术手段，而不是我们究竟想证明什么。

同一个验收点可以由页面、接口、文件、截图或人工检查提供证据。框架负责表达需求、前提、状态、行为、观察、选择和快照；具体项目负责决定使用什么驱动器、哪些证据可信，以及如何初始化和保存自己的系统。

## 设计目标

- 让需求和验收点成为测试组织的第一层结构。
- 让环境前提以“与/或”关系显式存在，而不是藏在测试说明里。
- 用可组合的状态和行为复用前置过程。
- 把会改变后续流程的业务选择形式化，并在执行前确定。
- 让观察返回证据，而不是只留下一个真假断言。
- 允许长流程在稳定边界保存快照，并从该位置继续执行。
- 通过 TypeScript 对象引用连接模型，不要求维护业务 ID。

## 分层边界

`src/model/test-requirement` 只包含与具体项目无关的框架：

- `model.ts`：需求、验收点、状态、行为、观察和流程。
- `choice.ts`：选择、约束、合法方案枚举和可达图分析。
- `executor.ts`：元数据、上下文、模型检查、执行和快照续跑。
- `snapshot.ts`：快照目录、清单及创建/恢复协议。
- `index.ts`：公共导出。

项目专属定义不进入这个目录。例如具体项目可把依赖枚举、分支选择、初始状态和数据库快照实现放在 `test/requirement/metadata`，把业务需求、页面行为和流程分别放在 `requirements`、`flows` 和 `scenarios`。

这样的边界很重要：框架不能知道某个项目使用 Playwright、SQLite 或 ADB，也不能依赖项目的页面辅助函数。

## 核心模型

```text
需求
└── 验收点 ──声明──> 验收手段与依赖方案
                       ▲
流程 ──覆盖引用────────┘
├── 给定状态
└── [行为 | 观察]...

初始状态 + 行为1 + 行为2 = 给定状态
```

### 需求与验收点

`需求`描述想要成立的业务能力，并引用一个或多个`验收点`。验收点是最小的验收承诺，包含：

- 描述；
- 验收手段：`自动`或`人工`，只要过程中必须有人参与就属于人工；
- 依赖方案：外层为“或”，每个内层为“且”。

例如：

```ts
依赖方案们: [
  [支付沙箱, 安卓手机],
  [苹果调试程序, 苹果手机],
]
```

含义是“支付沙箱且安卓手机”或者“苹果调试程序且苹果手机”。空的方案列表表示没有额外依赖。依赖条件的枚举由项目定义，框架只保留泛型。

### 状态与行为

状态保存的是“从初始状态开始依次施加哪些行为”的定义，而不是一份任意可变的数据副本。

```ts
let 已登录 = 初始状态.施加('管理员已登录', 登录行为)
let 已建订单 = 已登录.施加('订单已建立', 创建订单行为)
```

`状态 + 行为 = 新状态`通过有序行为数组的连接实现。连接满足结合律，因此状态可以安全地分段定义和复用。状态本身不执行操作，执行器在流程开始时展开并依次执行它所引用的行为。

每个项目必须在元数据中声明唯一的初始状态及其准备函数。正常运行时，执行器总是完整执行初始状态准备，不复用上一次测试留下的数据。

### 行为、观察与证据

`行为`操作系统并可能改变状态。`观察`读取系统并返回结构化结果，但在模型语义中不改变状态。

观察结果必须包含：

- 是否通过；
- 失败时的原因；
- 一项或多项证据，包括手段、描述、可选内容及附件路径。

框架不预设证据一定来自页面或接口。项目可以在元数据中配置`证据策略`收紧允许手段。实际业务验收项目通常只允许页面、页面流程结果、下载文件和截图，因此业务验收保持纯黑盒；初始化和快照属于测试基础设施，不作为业务证据。

### 流程

流程由一个给定状态和有序的`行为 | 观察`数组组成，并通过对象引用声明覆盖哪些验收点。

流程至少包含一个观察，也至少覆盖一个验收点。覆盖关系表示“这个流程打算为这些验收点提供证据”，不表示仅仅执行完行为就自动通过。

## 静态选择与分支

选择描述那些在测试开始前已经确定、并会影响后续业务路径的输入，例如物料来源、订单类型或加工顺序。

```ts
let 物料来源 = new 选择({
  名称: '物料来源',
  说明: '决定生产物料由平台采购还是由客户提供。',
  选项们: [
    { 值: '平台采购', 标签: '平台采购', 说明: '平台负责生成采购任务并跟进物料到位。' },
    { 值: '客户整单来料', 标签: '客户整单来料', 说明: '客户提供整单生产物料。' },
  ] as const,
})
let 方案 = new 选择结果([选择值(物料来源, '平台采购')])
```

项目交互入口应使用选择和选项的业务说明，不直接向用户暴露例如 `DB_ENUM_VALUE` 等难以理解的内部枚举值。简单模型仍可使用 `new 选择(名称, 可选值们)` 的简写形式。
条件选择使用 `可不出现: true`，并由选择约束通过 `是否出现()` 描述它在什么条件下必须出现。不使用“不适用”之类占位值；未满足出现条件时，该选择不存在于选择结果中。

选择具有以下约束：

- 在运行开始前一次性注入满足约束的`选择结果`，其中包含全部必选项和当前应出现的条件选择；
- 流程只能通过`上下文.选择`读取，不能在中途修改；
- 页面或接口行为必须真正由选择值驱动，选择不能只是场景标签；
- 选择、约束和场景之间使用对象引用，不使用手写 ID。

`选择约束`可以引用多个选择。例如“只有当支付方式选择了信用卡时，才需要选择分期期数”。框架会枚举合法完整方案，并构造按选择声明顺序展开的前缀图。

可达分析检查三件事：

1. 至少存在一个合法完整方案；
2. 每个声明的选择值至少出现在一条根到叶路径中；
3. 图中没有死路，所有合法完整方案都有对应叶节点。

交互入口可以调用`获得可延伸选择值们()`，只展示仍能延伸为合法完整方案的选项。选项是否出现以及值是否可选必须只由需求模型的合法性决定，不应根据已有测试场景裁剪；场景登记只决定当前合法选择下是否有可执行验收方案。项目应在套件初始化时重新执行可达检查，因为选择和约束会随代码变化。

选择定义可达与测试覆盖是两个概念：前者证明模型自身没有不可到达的值，后者证明合法业务分支已有场景提供证据。一个合法方案存在，不代表它已经被测试实现。

## 快照

快照用于减少长流程末端调试时重复执行前置步骤的成本。项目元数据提供：

- 快照根目录；
- 创建回调；
- 恢复回调。

流程步骤可以请求在自己成功结束后保存快照：

```ts
new 行为('完成采购入库', async (上下文) => {
  await 通过页面完成采购入库(上下文.系统)
  上下文.快照.保存('采购入库完成')
})
```

执行器会在步骤成功返回后生成 UUID，建立独立目录，调用项目创建回调，并写入`snapshot.json`。清单记录流程、给定状态、已完成步骤、下一步骤、选择方案和依赖条件。

恢复时执行器会：

1. 校验快照属于当前流程；
2. 校验给定状态、已完成步骤及其顺序没有漂移；
3. 校验选择方案一致、所需依赖仍满足；
4. 完整执行项目初始状态准备；
5. 调用项目恢复回调；
6. 跳过快照前已经完成的步骤，从下一步骤继续。

框架只持久化清单。数据库、文件、外部设备状态以及需要续跑的业务上下文都由项目回调负责。后续步骤需要的数据必须能够从恢复后的系统重新观察得到，或者由项目一并持久化；不能只存在于进程内对象中。

## 执行上下文

流程获得只读入口组成的上下文：

```ts
type 流程上下文<系统上下文, 依赖条件> = {
  readonly 系统: 系统上下文
  readonly 依赖: 依赖条件集<依赖条件>
  readonly 选择: 选择读取器
  readonly 快照: 快照入口
}
```

`系统`由项目注入，可以包含浏览器页面、设备控制器或其他驱动器。模型不限制技术手段，但项目的证据策略可以限制哪些观察结果有资格作为验收证据。

## 执行生命周期

一次正常流程执行遵循以下顺序：

```text
模型结构检查
→ 选择完整性与约束检查
→ 依赖检查
→ 准备项目初始状态
→ 展开并执行给定状态行为
→ 依次执行流程行为与观察
→ 校验证据策略
→ 在请求快照的步骤边界创建快照
→ 返回流程执行报告
```

模型检查还会拒绝重复登记、未知引用、非初始状态根、没有观察的流程、未登记的验收点、无效选择空间等结构错误。

## 黑盒原则

纯黑盒是项目策略，不是框架对所有项目的硬编码限制。推荐遵循以下区分：

- 初始化可以清库、执行 init、应用配置，因为它建立测试前提；
- 快照可以复制或替换数据库，因为它是调试基础设施；
- 业务行为应通过真实用户入口操作系统；
- 业务观察应从用户可见结果取证；
- 初始化或快照产生的数据不能冒充业务功能正确的证据。

如果某个项目允许接口证据，可以将接口加入证据策略；这不会改变需求、流程或选择模型。

## 为什么不使用业务 ID

需求、验收点、选择、状态和流程都通过 TypeScript 对象引用关联。这样可以让重命名和重构受到类型系统保护，也避免为大量 AI 生成的测试人工编排、同步和排查字符串 ID。

UUID 只用于一次落盘快照，因为快照需要跨进程定位物理目录；它不参与业务模型引用。

## 最小示例

```ts
let 手机 = new 选择('手机', ['安卓', '苹果'] as const)
let 可以登录 = new 验收点<依赖>({ 描述: '用户能够登录', 验收手段: '自动', 依赖方案们: [[依赖.浏览器]] })
let 登录需求 = new 需求({ 名称: '登录', 描述: '合法用户可以进入系统', 验收点们: [可以登录] })

let 登录流程 = new 流程({
  名称: '使用页面登录',
  给定状态: 初始状态,
  步骤们: [
    new 行为('提交账号密码', async ({ 系统 }) => await 系统.提交登录()),
    new 观察('观察首页', async ({ 系统 }) => ({
      通过: await 系统.首页可见(),
      证据们: [{ 手段: '页面', 描述: '登录后首页可见' }],
    })),
  ],
  覆盖验收点们: [可以登录],
})
```

测试运行器只是这个模型的适配器。它负责提供系统上下文和命名步骤展示；需求模型本身不依赖 Playwright、Vitest 或其他具体测试框架。
